# Safe restart coordinator foundation

This slice is pure policy and I/O capability bookkeeping. `SafeRestart.h` describes the planned runtime API; its SDK adapter and scheduling callers are not wired yet. There is no new restart, controller access, installer or manual upload flow. The raw filesystem application-upload prerequisite and Sid's web-assets packaging decision remain unresolved.

`RestartPolicy` binds one intent to settings uncertainty epoch, model failure epoch and a non-reused generation. Asynchronous submission is a bounded mailbox using the last loop-published observation; it is not admitted restart authority. Loop admission compares fresh observations, then starts a bounded delay of at most 60 seconds. The clock is monotonic boot time with a high-water mark. Backward time, epoch changes, later queued operations, cancellation or a failed final model save terminate the intent. Clearing uncertainty or successful automatic model-save recovery cannot resurrect it. A new explicit request is required.

`RestartCoordinator` splits work into reserve, external I/O and completion phases. One runtime mutex must cover all coordinator and `StorageLeaseGate` calls, but it must never remain held for model serialization, SDK calls, cleanup or shutdown. Each work item retains a generation-bound storage capability while I/O runs outside the mutex. Completion verifies both intent and lease identity. Cancellation leaves the storage capability held until its original owner finishes cleanup. Stale completion/release cannot admit or unlock a replacement owner. The final capability stays held through checked model I/O and shutdown, and restart can be taken only once.

The storage gate grants exclusive I/O use for model writes, restart and update replacement. It neither authenticates a user nor grants updater ownership. An exclusive update capability cannot serialize the model. Every ordinary model commit will acquire a model capability; a coordinator commit can borrow its validated restart capability through the same checked writer. Every controller commit outcome, including automatic retries, must notify the coordinator. Failed/uncertain results advance model history; success clears recovery need without rewinding history.

Future manual/install/restore admission must acquire the existing `GitUpdateClass` owner first and the storage capability second, then release in reverse order on all failure paths. This does not create another update worker or installer. Read-only metadata checks hold no storage capability or radio freeze; concurrent staging may conservatively invalidate an attestation result.

## Runtime wiring and raw-filesystem dependency

Runtime integration must replace every scheduling writer and both shutdown/restart sites. The legacy `rebootDelay` flag will be a read-only compatibility mirror outside the coordinator. `restartPending()` includes both mailbox and admitted timer so local mutations cannot bypass admission simply because their queue is empty. Completion replies must report actual admission, with typed reasons for settings uncertainty, model failures and queued work. A failed request must never retry model I/O on every loop pass.

A dirty-model check cannot safely race an existing application upload. An activity flag is insufficient because upload could begin between the check and serialization. The same exclusive storage capability must cover manual Update ownership and coordinator I/O/shutdown. Moreover, raw filesystem replacement invalidates the old LittleFS mount: post-upload recovery must never serialize through that old mount.

The dependent raw-filesystem design therefore needs explicit staging and lifecycle review before any routing: bounded image storage without internal fallback, fresh loop-owned admission, all filesystem handles inventoried and drained before unmount, no formatting, owned bounded writes/abort, explicit remount of the new image, asset verification, then checked serialization of the current running model. Retain exclusion through remount and recovery. A failure after replacement is applied/uncertain and must not claim rollback or schedule an automatic restart. Missing remount/recovery evidence leaves typed unavailable/frozen state for explicit recovery. No old backup or RF/counter operation may be replayed. Generic boards without sufficient PSRAM need their own reviewed protocol; no silent fallback is provided here.

## Offline evidence

Native tests first reproduced epoch/clock/queued-work resurrection and premature release/admission, then passed after the policy and coordinator checks. They cover delayed asynchronous requests, cancelled I/O retaining exclusion, stale generation tokens, model failure followed by recovery, failed final commit, one-shot shutdown permission, invalid delays and unsafe observations. These are pure fake/local tests, not evidence of SDK mount lifecycle, actual storage latency, TLS, RF, motors or physical recovery. The runtime and manual-upload stages remain incomplete.
