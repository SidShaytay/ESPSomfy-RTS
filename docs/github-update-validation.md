# Evidence required to accept verified GitHub updates

The implementation addresses the failure mechanisms in ADR 0007 for the explicit PSRAM-equipped release profiles. Hardware acceptance is still pending Sid's approved service window. Host tests and successful compilation do not demonstrate real TLS handshake peaks, uninterrupted RF timing, power-failure recovery, or motor/state continuity.

| --- | --- | --- | --- |

Additional issue #12 requirements extend beyond the original ADR:

- Exact compiled board/layout/revision/release/application identity and runtime image checks prevent generic S3 substitution. The release packager refuses dirty, untagged, relabelled or changed-after-build sources. SHA256 is bound to metadata fetched over authenticated GitHub HTTPS; it is not an independent signing key.
- Each profile's generated bootloader size/digest is compared with installed flash bytes. Release metadata must require the same bootloader digest. Missing rollback configuration, altered bytes or read/hash failure fail closed; `tools/test_update_bootloader.py` and `tools/test-update-bootloader.sh` cover those controls. Only a live failure/rollback test establishes recovery on this physical controller.
- Firmware-only updates preserve the shared filesystem and NVS layout. Exact packaged web-asset compatibility must be established before enabling installation and health confirmation; an application version label alone does not prove unchanged assets. Initial bootstrap of the new web-asset manifest is a separate explicitly approved operation.
- The loop saves and validates current controller configuration before quiescing. New firmware must satisfy the postboot health interval or roll back. Actual linked-remote counters, shade identities/calibration, and absence of unexpected RF/motor commands require private fresh snapshots and live observation. Historical backups are not current acceptance evidence.

Use [the service-window plan](github-updates.md#approve-a-specific-service-window) to record exact artifact hashes, approved operations, recovery prerequisites, observed measurements and outcomes. Keep issue #12 open until its publication and live acceptance requirements have been met; leave HA installation controls disabled until then.
