# Web-to-LCD capability matrix — issue #25

Inventory baseline: fetched main `fc5a2947928fdf855185f77ecaae69c00b677156` (2026-11-08). This is a **design inventory, not implementation or parity evidence**. Every LCD workflow below is proposed unless explicitly described as existing. No live device was accessed. No row authorizes RF, GPIO, model persistence, flashing, HA changes or hardware testing during development.

## How to read the matrix

The current web application is `data-src/index.html` and `data-src/index.js`; `data-src/js/views.js` adapts the protocol model. Most operations use protocol 2 over `/ws`; the complete operation registry is `src/ProtoSchema.h:20`. Command requests use `parseShadeOp` / `ShadeRequests::run` (`src/ProtoOps.cpp:157`, `src/ShadeRequests.cpp:40`); edits use `expandEditPayload` and loop-owned `applyModelEdit` (`src/ProtoEdits.cpp:129`, `src/SomfyJson.cpp`); settings use `expandSettingsPayload` / `runDeviceOp` (`src/ProtoSettings.cpp:188`, `src/DeviceOps.cpp:217`). LCD code must call shared domain seams with typed data, never loopback HTTP, web handlers, or direct radio/rolling-code manipulation.

Current web authorization (`W`): None permits access; PIN or username/password security requires a token for all socket access and protected HTTP endpoints (`src/entryPoints/Web.cpp:96`, `src/outputs/ProtoSocket.cpp:265`, `src/HttpAccess.h:31`). Public assets/login context/login/SSDP do not provide privileged access. There is no web role distinction between everyday controls and administration. **W does not protect the encoder or Back button.**

LCD authorization (`V`, `C`, `A`, `T`): V = non-sensitive view; C = everyday control; A = local administration; T = A plus the proposed authenticated companion transfer session. Sid approved the same configured web credential for C and A, with 120-second inactivity expiry; STOP requires unlock after expiry. None mode remains open, with action-specific risky confirmations. PIN/password modes require unlock for controls and administration. Use an independent device-wide throttle with the current web schedule (fifth failure locks for 30 s, subsequent failures double up to 15 min, one-hour quiet reset); volatile failure state resets at reboot, an acknowledged limitation. Transfer design remains pending. An asterisk means an action-specific confirmation showing the current entity and consequence. These are requirements to implement, not claims that local auth already exists.

Input abbreviations: list = rotary scroll, push select, Back return; edit = rotary changes a draft, push accepts field, explicit Save/Cancel; confirm = default Cancel and deliberate push on the named action. **Turning the wheel never sends a command or saves.** Every submission must revalidate IDs, RF identities, capabilities, membership, authorization, update/restore gates and queue capacity on the owning loop.

Tests named below are acceptance cases to add/extend, not tests already run or proofs of coverage. Existing useful host seams are `test/test_shaderequests`, `test/test_protoops`, `test/test_protoedits`, `test/test_protosettings`, `test/test_modeleditor`, `test/test_localui`, `test/test_configimport`, `test/test_secrets`, `test/test_loginthrottle`, `test/test_httpaccess`, `test/js/{model,views,client}.test.js`, and the adapter/runtime/capture/renderer harnesses invoked by `tools/test-local-ui-adapter.sh` and `tools/test-status-panel.sh`. Do not run `test/e2e` against an in-service controller.

## Existing implementation and unresolved product decisions

At this baseline `LocalUi.h:19` has three fixed targets; `LocalUiAdapter.cpp:65` reads shades 1/2 and group 1, permits paired RTS only, and exposes Up/Stop/Down. This does not satisfy the dynamic matrix. Local main's later `a493d50` shared-group STOP fix must be independently preserved when starting from fetched remote main; old branch code is not acceptance proof.

Before implementing the affected flows, resolve these with Sid:

1. **Local authentication scope:** Sid has selected reuse of the same web credential for controls and administration, with a 120-second inactivity expiry and an attempt limit; STOP also requires unlock after expiry. None mode remains open with action-specific confirmations for risky actions. Still specify visibility of identifying status before unlock. Avoid a hidden physical bypass for secured mode.
2. **Unlock/recovery:** use the selected shared credential; use the selected independent device-wide web throttle schedule and volatile state, documenting reboot reset; specify credential-change invalidation and recovery without wiping configuration/counters. The selected inactivity timeout is 120 seconds; do not silently extend it for STOP. Existing web PIN permits four characters, not necessarily only decimal digits.
3. **Text/secret entry:** bounded rotary character picker can handle existing byte-limited fields but is slow; companion entry needs authenticated transport. Decide whether both are required. Never reveal stored secrets; explicit retain/replace/clear avoids confusing blank-entry semantics. Screenshots of secret entry, unlock/transfer frames and sensitive diagnostics must be suppressed, not merely rely on password masking.
4. **File transfer:** agree authenticated companion workflow, transport trust, session binding/expiry, who confirms restore/update, and what Cancel means after upload/write begins. A QR/URL alone does not securely authorize a transfer. No SD promise without board/bus design.
5. **Baseline gaps:** light's visual-only web button, group step-size omission, API-only position correction/raw-remote operations, and missing #12 GitHub service need explicit disposition. Document approved equivalence/deferral per row; never mark unsupported as done.
6. **Dangerous remote tools:** whether all current button chords/sensor simulation are exposed under administrator confirmation and what text makes physical side effects clear; do not treat web availability as blanket authorization to execute them during development.

All workflow implementations remain proposed/unimplemented at this design checkpoint; the authentication decisions above are approved requirements. Native/compiler/renderer evidence and physical-board acceptance are separate. Firmware builds cannot establish heap fragmentation, combined TLS/staging/capture stress or real loop/SPI timing on hardware; those measurements remain a later explicitly authorized stage.
