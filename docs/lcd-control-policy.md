# Local control capability and request policy

`LocalControlPolicy` is a pure typed boundary used by LCD menus and the loop adapter. It does not look up model entities, allocate identities, mutate motion, submit requests, touch GPIO, use RF or save configuration. `ControlAction` retains `up=0`, `stop=1`, `down=2`; later values explicitly distinguish percentage/tilt, intentional MY, 80-bit Favorite, Toggle, Step and sun-flag actions.

Use `controlCapabilities(descriptor)` / `allows(action, descriptor)` to build menus, then `prepareControlRequest` again immediately before the adapter submits a freshly validated model target. Only `ControlResult::done` produces an output request. On unsupported/invalid/idle, the output stays unchanged; callers must check the result. IDs are stable model IDs in 1..254, not indices or RF addresses. A target is strictly 0..100; unused target is -1. Steps are 1..127; unused step is zero. Validation occurs before narrowing, so an invalid percentage cannot become an implicit default-MY request.

The descriptor carries actual type/tilt/protocol, effective RF bit length, pairing, sensor capability and current estimated motion. RF RTS/RTW/RTV require a paired shade and valid 56/80-bit setting. GPIO relay/remote operation does not acquire an RF-pairing or bit-length requirement. Ordinary commands follow the web controls and shared behavior: one-button garage/gates and single dry contact expose Toggle; two-button dry contact exposes Up/Down; ordinary movers expose guarded STOP and intentional MY. STOP uses the reviewed MY behavior only while moving. Tilt STOP additionally requires tilt motion. Reported nonzero tilt modes are honored where the existing web positioner/hold and shared behavior support them; tilt-only devices have no lift target. 80-bit Favorite/Step are RF actions, with their existing exact opcodes. No light opcode is invented.

For a group, the adapter must validate every member's identity/protocol/context and set `memberCount=0` if membership is empty, incomplete, stale or RF-incompatible. Otherwise intersect every member's capabilities into `commonActions`. Group-supported daily actions are Up/Stop/Down/MY/Step; unsupported group position/tilt/Toggle/Favorite paths are not synthesized. The group's `sunSensor` is an any-member sensor aggregate, matching the web behavior rather than an all-members intersection. A mixed group can therefore expose Sun On/Off even with no common movement action. GPIO groups have no shared member GPIO trigger path and are not represented as valid RF group operations.

The adapter still owns fresh authorization/generation/capability checks, RF identity, exact membership, runtime admission/backpressure and the scoped STOP lease. It must preserve mixed/idle-member STOP safeguards rather than blindly submit a group MY. Percentage orientation and movement semantics remain in `ShadeRequests` / `ShadeBehaviour`; the policy does not duplicate them.

The separate group-step correction propagates the requested `stepSize` from `SomfyGroup::sendCommand` through `SomfyShade::processInternalCommand` to `ShadeBehaviour::onGroupCommand`. Member estimates now use the same existing step math as the transmitted frame, with zero retaining the legacy protocol default of one. Native fake-MotorLink cases compare both directions, sizes 0/1/3/127 and lift/integrated/tilt-only estimates, and ensure no second member RF request is generated.

Tests cover all 17 device categories, five protocols, five tilt modes and both RF lengths (850 descriptors), malformed enums/lengths, unsupported action values, strict ID/target/step bounds, exact request types/opcodes, idle stops, unchanged failure outputs and mixed group/sensor capabilities. Bypassing target validation causes the invalid-percentage regression to fail; forcing group steps back to one fails the requested-three-step estimate case. All tests use synthetic model data/fake sinks.

This module does not establish physical support or complete web/LCD parity. In particular, an existing shared GP_Remote one-button Toggle translation gap was reported separately: 56-bit Toggle becomes MY in `ShadeBehaviour`, while the GPIO MY handler skips one-button devices. Do not fix that by inventing a different request in this policy; its shared GPIO boundary needs its own reviewed regression/fix before claiming complete GPIO control support. GP_Relay separate/euromode tilt handling also requires its own GPIO-boundary regression because the current driver follows tiltDirection only for integrated/tilt-only. Advanced virtual-remote commands that the group model does not track remain a distinct administration flow with honest semantics.
