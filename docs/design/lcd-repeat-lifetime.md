# LCD everyday remote: repeat lifetime proposal

Status: scheduler cancellation, typed receipts, retained LCD ownership and terminal forwarding are implemented. Back, authorization/context changes, timeout and graphics recovery cancel remaining admitted repeats. The hold/release interaction remains unimplemented. No hardware testing. This proposal requires the interaction decision below before UI implementation; it is not a claim that finite batches satisfy the accepted release requirement.

## Acceptance gap and interaction decision

The normative issue discussion requires release, Back and timeout to stop **future repeats**. Current `repeatValue` still starts an explicitly confirmed finite batch. `runLocalControl()` now retains its fresh-command receipt until a matching terminal event; Back and invalidation reach that exact job. Physical release does not yet cancel future frames, so the full requirement remains open.

Proposed interaction: select an explicit maximum count and action/step, review the exact target and count on a protected completed frame, then deliberately **hold to send**. Release cancels the unsent remainder; reaching the maximum ends the job even if still held. Back, authorization expiry, input/presentation timeout, target/configuration/history change and display recovery also cancel that same owned job. A new press after release requires fresh admission. Keep ordinary one-shot controls unchanged. This changes the present click-to-send batch interaction and needs Sid's agreement. Keeping a finite click-to-send batch would require explicitly changing the normative requirement; it is not an equivalent implementation.

Cancellation only stops further radio frames. It does not stop an already moving shutter and never sends MY/STOP, because MY can invoke a favourite. Finish the current frame; a cancellation that races the scheduler start may permit the initial frame, and a cancellation racing a frame-boundary decision may permit the frame already committed. Do not promise instantaneous RF silence or a human emergency stop. Input is polled on the existing UI loop, so a blocked loop delays observing release.

## Bounded implementation plan

1. Implemented foundation: `RadioScheduler::cancel(ticket, now)` under the existing caller serialization. For a queued exact ticket, remove it and report one `dropped` outcome. For the taken ticket, mark the existing cancellation flag so `start()` refuses it if not yet started, or `keepSending()` refuses the next repeat. Preserve `started` followed by `aborted` for an on-air partial job; normal completion winning the race remains `finished`. Unknown, zero, repeated or terminal tickets are harmless. Do not flush other tickets, change queue ordering, recycle rolling codes, lose events, or add a queue/owner. Existing event reservation already covers these outcomes.
2. Implemented foundation: `Transceiver::cancelTx(ticket)` uses `TxQueueLock` and wakes the radio task after unlocking so a removed delayed head cannot strand unrelated work. The existing sole event consumer forwards outcomes after model processing; cancellation does not wait for `RadioLock` held by transmission. Reuse the existing frame-boundary predicate in `transmitJob()`. Avoid retaining an extra event consumer: the model loop remains the single collector and forwards terminal notifications to the local owner before clearing outcomes. No global suspend/flush.
3. Implemented: propagate the exact accepted ticket through the existing typed request/domain path with a local-only receipt output, leaving current bool/enum callers unchanged. The ticket already exists in `sendCommandAfter()`; Both command and repeat paths provide it. New LCD intents use command request types and a fresh rolling code even when the previous command matches; repeat request types preserve their intentional last-frame reuse. Group dispatch must preserve group-domain bookkeeping, not bypass it with a raw remote send. Reject unsupported/multi-job paths for this owned everyday repeat flow rather than infer a ticket from global state. Do not expose programming actions or GPIO repeat holds through this mechanism.
4. Implemented common lifetime: extend the existing local pending-control slot to retain the owned ticket after admission until terminal outcome. Retain its original exact context, security generation, original maximum count, protected presentation and intent token. Validate through terminal completion, with fail-closed cancellation on Back/auth expiry/timeout/context drift/recovery. Release/hold input remains pending. Admission and queued jobs retain the 5-second deadline; started jobs use a finite maximum of 188 + 141 × repeat milliseconds plus the same 5-second allowance, derived from the current 56/80-bit waveforms. No new owner or parallel intent slot. Distinguish queued, sending, cancelling and terminal states without claiming motor movement stopped. Preserve current StopLease and owner/lease locks; release does not create a STOP lease or modify it. A same-target explicit STOP cancels the old repeat and joins the global FIFO tail inside the same slot; the old ticket remains owned until its terminal event. Neither terminal-event order may clear or replay the STOP marker.
5. Add UI/controller+actual GFX/knob/FIFO tests proving release after admission reaches that exact ticket and count/action/target stay bound to the reviewed frame. Cover hold-to-max, release-before-admission, release-while-queued, take/start race, on-air cancellation, terminal-event race, Back, timeout/auth expiry, context change and recovery. Preserve independent GPIO operation during RF admission refusal, pending command accounting and completed-frame privacy guards.

Scope is E14 everyday virtual-remote repeats. Pairing, Set/Clear Favourite and guided programming/chord batches retain their reviewed finite protocol semantics; they must not be accidentally truncated by this local repeat cancellation.

## Implemented receipt foundation

`ShadeRequests::runOwnedRepeat()` returns an `owned_repeat_receipt_t` containing the exact accepted RF ticket. The dedicated backend hook refuses by default; ordinary request callers keep their existing behavior. The concrete model validates the explicit count, everyday command whitelist, RF protocol, bit length, Euro and step constraints before dispatch. Unsupported owned requests cannot fall back to an untracked command.

New-command receipts use the existing shade/group command path, preserving counter, flip, movement and group-member bookkeeping. Repeating the previous frame requires the current remote address, protocol, effective bit length, transformed command and step size to match; a changed identity or step sends a new command with its own counter and ticket. Receipts come from that invocation's actual transmission result, without a global last-ticket value or another event consumer. Existing GPIO boolean paths retain their behavior but are unavailable through the RF-owned API.

The compiled model harness covers new/repeated receipts, counters, flip and step binding, group bookkeeping, refusal without mutation and unsupported request rejection. Independent removal of the step-match condition fails the changed-step regression. Actual adapter/FIFO and encoder/GFX regressions now prove retained ownership, Back/auth/context/graphics/timeout cancellation, stale terminal isolation, long-job deadlines and explicit STOP behavior. The exact TX-consumer-prefix harness proves model-before-LCD forwarding and unlocked callbacks with no additional consumer. These remain offline observations; physical release input and hardware timing are still pending.
