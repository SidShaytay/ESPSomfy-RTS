# LCD everyday remote: repeat lifetime proposal

Status: design and deliberately failing regression checkpoint against main dcdb588 (4.5.0). No production implementation or hardware testing. This proposal requires the interaction decision below before UI implementation; it is not a claim that finite batches satisfy the accepted release requirement.

## Acceptance gap and interaction decision

The normative issue discussion requires release, Back and timeout to stop **future repeats**. Currently `repeatValue` submits the whole selected batch; `runLocalControl()` calls `ShadeRequests::run()` and immediately clears its pending slot. `cancelUnsubmittedLocalControl()` cannot reach the admitted RF job. The scheduler has global flush/suspend but no ticket-specific cancellation.

Proposed interaction: select an explicit maximum count and action/step, review the exact target and count on a protected completed frame, then deliberately **hold to send**. Release cancels the unsent remainder; reaching the maximum ends the job even if still held. Back, authorization expiry, input/presentation timeout, target/configuration/history change and display recovery also cancel that same owned job. A new press after release requires fresh admission. Keep ordinary one-shot controls unchanged. This changes the present click-to-send batch interaction and needs Sid's agreement. Keeping a finite click-to-send batch would require explicitly changing the normative requirement; it is not an equivalent implementation.

Cancellation only stops further radio frames. It does not stop an already moving shutter and never sends MY/STOP, because MY can invoke a favourite. Finish the current frame; a cancellation that races the scheduler start may permit the initial frame, and a cancellation racing a frame-boundary decision may permit the frame already committed. Do not promise instantaneous RF silence or a human emergency stop. Input is polled on the existing UI loop, so a blocked loop delays observing release.

## Bounded implementation plan

1. Add `RadioScheduler::cancel(ticket, now)` under the existing caller serialization. For a queued exact ticket, remove it and report one `dropped` outcome. For the taken ticket, mark the existing cancellation flag so `start()` refuses it if not yet started, or `keepSending()` refuses the next repeat. Preserve `started` followed by `aborted` for an on-air partial job; normal completion winning the race remains `finished`. Unknown, zero, repeated or terminal tickets are harmless. Do not flush other tickets, change queue ordering, recycle rolling codes, lose events, or add a queue/owner. Existing event reservation already covers these outcomes.
2. Expose narrow `Transceiver` ticket cancellation/status wrappers using `TxQueueLock`; cancellation must not wait for `RadioLock` held by transmission. Reuse the existing frame-boundary predicate in `transmitJob()`. Avoid retaining an extra event consumer: the model loop remains the single collector and forwards terminal notifications to the local owner before clearing outcomes. No global suspend/flush.
3. Propagate the exact accepted ticket through the existing typed request/domain path with a local-only receipt output, leaving current bool/enum callers unchanged. The ticket already exists in `sendCommandAfter()`; `repeatFrame()` currently discards `job.ticket`, so both command and repeat paths must provide it. Group dispatch must preserve group-domain bookkeeping, not bypass it with a raw remote send. Reject unsupported/multi-job paths for this owned everyday repeat flow rather than infer a ticket from global state. Do not expose programming actions or GPIO repeat holds through this mechanism.
4. Extend the existing local pending-control slot to retain the owned ticket after admission until terminal outcome. Retain its original exact context, security generation, original maximum count, protected presentation and intent token. Continue validating while held, with bounded hold lifetime and fail-closed cancellation on release/Back/auth expiry/timeout/context drift/recovery. No new owner or parallel intent slot. Distinguish queued, sending, cancelling and terminal states without claiming motor movement stopped. Preserve current StopLease and owner/lease locks; release does not create a STOP lease or modify it. Never silently replace an active owned ticket with a new request.
5. Add UI/controller+actual GFX/knob/FIFO tests proving release after admission reaches that exact ticket and count/action/target stay bound to the reviewed frame. Cover hold-to-max, release-before-admission, release-while-queued, take/start race, on-air cancellation, terminal-event race, Back, timeout/auth expiry, context change and recovery. Preserve independent GPIO operation during RF admission refusal, pending command accounting and completed-frame privacy guards.

Scope is E14 everyday virtual-remote repeats. Pairing, Set/Clear Favourite and guided programming/chord batches retain their reviewed finite protocol semantics; they must not be accidentally truncated by this local repeat cancellation.

## RED evidence and remaining checks

`test/test_radioscheduler/test_radioscheduler.cpp` adds three real production-scheduler cases: admitted queued ticket removal, taken-before-start refusal, and on-air next-repeat refusal, each preserving unrelated work and exact ticket outcomes. A temporary SFINAE test adapter calls the proposed API when present; on current main it deliberately performs the current no-op cancellation so the defect is a runtime assertion failure rather than a missing-method compilation error. Remove that fallback when implementing the API. The focused native run fails at all three intended runtime assertions on current production code; all existing listed scheduler cases pass. PlatformIO reports the nonzero Unity result as ERRORED/SIGQUIT. Evidence: `/tmp/i25-repeat-lifetime-red.log` (local, not committed). The tests do not emulate radio transmission or claim electrical timing evidence.

Next foundation checks: duplicate/unknown cancellation, cancellation at event capacity, same-remote rolling-code order, terminal races, suspension/restart accounting and 56/80-bit boundary handling. Then actual-model receipt/outcome tests and actual UI/FIFO integration. Production changes require independent review and relevant broad integration checks before main; physical RF/motor testing remains separately authorized.
