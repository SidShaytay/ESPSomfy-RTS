# Keep GitHub updates on a maintained base

**Your fork can retain LILYGO support and device-side GitHub release updates while adopting cjkas improvements.** The clean long-term direction is to move the small hardware profile onto a maintained base and implement pull updates as a separate service. Your existing PR does not apply directly to cjkas, and restoring the old updater unchanged would restore its security and reliability problems. Selective fixes on the current base remain a reasonable interim path. The remembered Daybreak Blue report was not located; Daybreak Blue is an OpenAI access program, and a private scan report could exist outside public GitHub. No firmware, controller, network or motor changes were performed.

## The byte match confirms an export copy was captured

The freshly downloaded native configuration export contained **1,228 bytes**. The firmware's `/backup` handler first writes `controller.backup` into LittleFS, then sends that file to the browser/client. The backup verification searched the captured 16 MB image and found the complete 1,228-byte sequence unchanged inside its LittleFS region. That confirms the export copy is included in the raw snapshot. It is **not independent extraction and decoding of the authoritative `shades.cfg`, nor a restore test**. The standalone filesystem unpacker still needs investigation. Raw NVS was captured separately; Wi-Fi credentials are outside the native export and were not validated by this byte-match test. ([Backup handler](https://github.com/SidShaytay/ESPSomfy-RTS/blob/718b7d4/Web.cpp), [record writer](https://github.com/SidShaytay/ESPSomfy-RTS/blob/718b7d4/ConfigFile.cpp))

## The LILYGO knowledge transfers, but PR #10 does not

Read-only patch-application checks against cjkas v4.0.2 failed, including an attempt to account for the move into `src/`. The old monolithic `Somfy.cpp` and `.ino` have been replaced by startup, transceiver, scheduler and GPIO modules. cjkas also changes Arduino/core/dependency versions and radio concurrency. **Reuse the fixed pin assignments, power/filter sequencing, reservation rules and tests; adapt their integration points.** ([Our PR](https://github.com/SidShaytay/ESPSomfy-RTS/pull/10), [stable source](https://github.com/cjkas/ESPSomfy-RTS/tree/v4.0.2/src))

One difference is semantic: our readiness probe reconfigures SPI pins, while cjkas's patched vendored SmartRC driver explicitly avoids doing so after Arduino 3 owns the SPI pins, because it can stop the S3 bus. Its radio accesses also use a mutex and scheduler. Copying our old radio code wholesale would bypass these improvements. ([Driver](https://github.com/cjkas/ESPSomfy-RTS/blob/v4.0.2/lib/SmartRC-CC1101-Driver-Lib/ELECHOUSE_CC1101_SRC_DRV.cpp), [transceiver](https://github.com/cjkas/ESPSomfy-RTS/blob/v4.0.2/src/Transceiver.cpp))

The migration also changes partition offsets and HA's API/socket contract. cjkas reads format-24 backups, but its restore policy can take a file counter lower than existing NVS; ours retains the higher counter. Reader support therefore does not prove safe import. A Plus release environment, binary-size checks and latest-counter import tests are needed before installation. No cjkas Plus build or hardware test was performed. ([Partitions](https://github.com/cjkas/ESPSomfy-RTS/blob/v4.0.2/esp32_3MB.csv), [counter policy](https://github.com/cjkas/ESPSomfy-RTS/blob/v4.0.2/src/RollingCode.h), [migration/API requirements](https://github.com/cjkas/ESPSomfy-RTS#api-and-ports))

## Preserve pull updates as an intentional fork feature

Keeping your repository and adopting cjkas as an upstream source are compatible choices. The recommended long-term arrangement is **cjkas base + small Plus profile + separately maintained GitHub updater**. A bounded interim release can instead harden the existing base while retaining its current HA contract. Repeatedly merging structural cjkas changes backward into the old monolith would increase conflict and maintenance costs.

The replacement updater should authorize and enqueue a job, then perform bounded streaming downloads outside server callbacks. Require certificate/hostname verification, exact Plus/partition manifests, trusted hashes and preferably device-verified signed manifests. Start with firmware-only updates to the inactive application slot. Two application slots do not make a shared filesystem replacement atomic: rollback must preserve compatible configuration, credentials, identities and counters. These are proposed engineering requirements, not implemented capabilities. ([cjkas removal rationale](https://github.com/cjkas/ESPSomfy-RTS/blob/f17eb4c7bbf68b4bd64456be415022746e698f1f/docs/adr/0007-no-github-update.md), [ESP-IDF OTA](https://docs.espressif.com/projects/esp-idf/en/stable/esp32s3/api-reference/system/ota.html))

Implement this in reviewable stages under issue #12: board/build and state migration; a finding-to-fix regression matrix; versioned compatible release artifacts; authenticated background pull OTA; then filesystem recovery. The raw backup is a recovery input, not proof of migration safety. Preserve issue #7's open state and the prohibition on motor tests until the user explicitly resumes physical verification.
