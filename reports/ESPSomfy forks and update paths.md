# Active forks offer better update paths

[Issue #12](https://github.com/SidShaytay/ESPSomfy-RTS/issues/12) now tracks fork versioning, release packaging and safe LILYGO updates. **cjkas/ESPSomfy-RTS is the strongest maintained candidate by measured recent development volume and stable-release activity; xkain is another active option.** Upstream development is dormant, although formal abandonment is not established. Other forks already address version stamping and fork-owned update channels, so we should inspect and reuse those solutions before building a new private updater. However, this research did not confirm a supported prebuilt/profile for our exact T-Embed CC1101 Plus. The practical next step is source evaluation, preserving our working hardware initialization and configuration—not immediately flashing a different S3 image. Findings are current to **November 3, 2026, America/Los_Angeles**.

Upstream's last default-branch commit was **August 19, 2024**, also the date of its latest prerelease, v2.4.7. Its latest stable release remains v2.4.6 from July 26, 2024. The repository is not archived, and the latest public maintainer issue comment found was January 20, 2025. Community discussion continues, but that is distinct from maintainer commits or releases. “Dormant upstream” is supported; an official abandonment or handover declaration was not found. ([Last commit](https://github.com/rstrouse/ESPSomfy-RTS/commit/eb75868adb92b3e6f5d3ead069f915d84a72efde), [releases](https://github.com/rstrouse/ESPSomfy-RTS/releases), [maintainer comment](https://github.com/rstrouse/ESPSomfy-RTS/issues/519#issuecomment-2603151859))

The survey inspected **154 retrieved direct forks** plus secondary and renamed derivatives. Recent main-branch commits were counted from August 5, 2026 UTC. Counts include merges, documentation, version increments, binaries and bots; they measure activity, not code quality. A recently pushed fork can still have an upstream-identical main branch.

The activity counts are reproducible from the projects' commit histories/API, and the survey is not an exhaustive examination of every descendant branch. cjkas is 399 commits ahead of original upstream and showed substantial merged-PR activity. xkain is 194 ahead and recently fixed backup settings parsing and timer rollover. Both larger projects remain heavily dependent on one maintainer by recent authorship. ([cjkas commits](https://api.github.com/repos/cjkas/ESPSomfy-RTS/commits?since=2026-08-05T00:00:00Z&per_page=100), [xkain commits](https://github.com/xkain/ESPSomfy-RTS/commits/main/), [linuxrrze commits](https://github.com/linuxrrze/ESPSomfy-RTS/commits/main/), [Pulpyyyy commits](https://github.com/Pulpyyyy/ESPSomfy-RTS/commits/main/))

**cjkas already solves much of the version/release problem**, but chooses a different update mechanism. Its release script derives firmware, application and cache versions from the release tag. Releases include checksums and chip-specific firmware/LittleFS assets. Accepted ADR0007 deliberately removes ESP-side GitHub OTA and filesystem recovery downloads; matching HA integration checks releases and provides update notifications, while installation uses manual upload or USB. That is an existing design to evaluate, not merely a repository-URL fix. ([Version script](https://github.com/cjkas/ESPSomfy-RTS/blob/main/.github/set_version.sh), [build workflow](https://github.com/cjkas/ESPSomfy-RTS/blob/main/.github/workflows/build.yaml), [ADR0007](https://github.com/cjkas/ESPSomfy-RTS/blob/main/docs/adr/0007-no-github-update.md))

For a smaller change to our current code, **linuxrrze's `GIT_REPO` centralizes all update/recovery repository URLs**. xkain already directs OTA to its own fork. Pulpyyyy also uses its own repository and selects S3 assets by 4MB/8MB flash size. None of those facts establishes exact board-profile compatibility. Also, `xkain/ESPSomfy-RTS-enhanced` is the **HA integration**, whereas `xkain/ESPSomfy-RTS` is the firmware. ([linuxrrze repository setting](https://github.com/linuxrrze/ESPSomfy-RTS/blob/main/GitOTA.h), [xkain updater](https://github.com/xkain/ESPSomfy-RTS/blob/main/src/GitOTA.cpp), [Pulpyyyy updater](https://github.com/Pulpyyyy/ESPSomfy-RTS/blob/main/src/GitOTA.cpp), [xkain HA component](https://github.com/xkain/ESPSomfy-RTS-enhanced))

**No inspected release confirmed our exact Plus power, RF-switch and fixed-pin sequence.** Generic ESP32-S3 targets and hardware presets do not prove that GPIO15 power and GPIO47/48 filter selection work on this board. Keep our observed-working profile until source and build evidence establish an equivalent. This is a bounded research finding, not proof that no unexamined branch supports it. ([cjkas build targets](https://github.com/cjkas/ESPSomfy-RTS/blob/main/platformio.ini), [xkain build targets](https://github.com/xkain/ESPSomfy-RTS/blob/main/platformio.ini), [Plus radio discussion](https://github.com/rstrouse/ESPSomfy-RTS/issues/598))

A full migration requires more than borrowing updater code. cjkas documents USB provisioning plus backup restoration when moving from original firmware/3.x to 4.x and requires a matching newer HA integration. Its restore code explicitly handles file rolling counters differently from the original max-of-file-and-NVS behavior. xkain main uses backup format 26 and linuxrrze format 25, versus our format 24; no import round trip was tested. ([cjkas migration notice](https://github.com/cjkas/ESPSomfy-RTS#readme), [restore implementation](https://github.com/cjkas/ESPSomfy-RTS/blob/main/src/ConfigFile.cpp), [xkain format](https://github.com/xkain/ESPSomfy-RTS/blob/main/src/ConfigFile.cpp), [linuxrrze format](https://github.com/linuxrrze/ESPSomfy-RTS/blob/main/ConfigFile.cpp))

I would evaluate cjkas first as the maintained baseline and xkain as the alternative, while cherry-picking a narrowly verified repository/version fix if that avoids an unnecessary migration. Before adopting any complete fork, finish the private raw configured backup in [issue #9](https://github.com/SidShaytay/ESPSomfy-RTS/issues/9), then validate partitions, the Plus profile, format-24 import, identities, group membership, rolling counters and matching HA integration in isolation. **No binary was installed, no device was changed and no motor commands were sent during this research.** Issue #7 remains open; physical verification still requires the user's explicit resumption.
