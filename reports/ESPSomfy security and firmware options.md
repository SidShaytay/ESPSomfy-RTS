# Maintained firmware improves security and options

**cjkas is the strongest candidate to evaluate for a maintained shutter controller; xkain offers a closer continuation of the original design.** The forks differ in their HTTP/API architecture, authentication enforcement, update strategy, UI and integration contracts—not merely release frequency. Source inspection found concrete security improvements, but no fork earned an independent security assurance from this review. Bruce officially supports the LILYGO T-Embed CC1101 Plus; selectable boot is plausible, while separate Bruce and Somfy images do not run concurrently. Rust is feasible on this ESP32-S3, but reliable RF timing, durable rolling counters and migration make a rewrite a separate embedded project. These findings are current to **November 3, 2026**; no device, network or motor changes were made.

The practical differences are:

| Firmware | Main distinction from original upstream | Consequence for this installation |
|---|---|---|
| Original rstrouse / our current base | Original synchronous Arduino web/API architecture and device-side GitHub updater. | Our Plus hardware initialization is verified; inherited web security and update assumptions need improvement. [Source](https://github.com/rstrouse/ESPSomfy-RTS/blob/eb75868adb92b3e6f5d3ead069f915d84a72efde/Web.cpp) |
| cjkas | Substantial asynchronous server/security redesign, newer toolchain, tag-derived versions, checksums, and removal of device-side GitHub downloads. | Strong platform candidate, but changed API/socket contracts, matching HA component and USB provisioning/restore make migration substantial. [Design](https://github.com/cjkas/ESPSomfy-RTS/blob/main/docs/adr/0007-no-github-update.md), [migration](https://github.com/cjkas/ESPSomfy-RTS#readme) |
| xkain | Responsive/localized UI, hardware/GPIO presets, own-fork OTA and original HA compatibility. | Less integration change; verify fixed Plus pins and updater security. [Project](https://github.com/xkain/ESPSomfy-RTS/blob/f55fb4cc5aa36ccbc9434ff2bd28a17efd04c628/src/README.md) |
| linuxrrze | Classic updater/recovery improvements, web installer, centralized repository and optional scheduled automatic updates. | Useful targeted changes; unattended updates are unsuitable until our board-specific artifacts are protected. [Source](https://github.com/linuxrrze/ESPSomfy-RTS/blob/e3c1289c3bd06722dd32654df84e8c9039d43040/GitOTA.cpp) |
| Pulpyyyy | RF command serialization/frame spacing, update preflight/recovery and flash-size-specific S3 images. | Interesting reliability work; 4MB/8MB selection is not exact Plus-profile validation. [Stable release](https://github.com/Pulpyyyy/ESPSomfy-RTS/releases/tag/v4.1.0) |

**None of the inspected alternative releases established turnkey support for our exact Plus power/RF-switch sequence.** Retain the observed-working profile until an equivalent build is verified. Likewise, changes in backup formats and restore-counter policies mean that successful compilation does not establish a safe migration. ([Build targets](https://github.com/cjkas/ESPSomfy-RTS/blob/main/platformio.ini), [restore policy](https://github.com/cjkas/ESPSomfy-RTS/blob/main/src/ConfigFile.cpp))

The most important security finding concerns authorization. Original upstream defines `Web::isAuthenticated`, but the inspected registered handlers do not call it to protect privileged routes/uploads. Its security settings also serialize password/PIN values and store them as NVS strings; encrypted storage was not established. Our hardware patch retained that design. **A functioning UI login is therefore not evidence that the underlying API is protected.** This is source evidence, not an active exploit test against the lilygo. ([Original routes](https://github.com/rstrouse/ESPSomfy-RTS/blob/eb75868adb92b3e6f5d3ead069f915d84a72efde/Web.cpp), [settings](https://github.com/rstrouse/ESPSomfy-RTS/blob/eb75868adb92b3e6f5d3ead069f915d84a72efde/ConfigSettings.cpp))

Several fixes are already released. **xkain v2.6.1** wraps routes and uploads in authorization guards and makes secret JSON fields write-only. **linuxrrze v2.4.19** adds middleware, but deliberately leaves most port-8081 control APIs public for legacy integrations. **Pulpyyyy v4.1.0** adds authentication and same-origin/Host defenses. Protection still depends on security configuration: all inspected defaults allow **Security=None**. ([xkain stable guards](https://github.com/xkain/ESPSomfy-RTS/blob/v2.6.1/src/Web.cpp), [linuxrrze stable middleware](https://github.com/linuxrrze/ESPSomfy-RTS/blob/v2.4.19/Web.cpp), [Pulpyyyy stable authentication](https://github.com/Pulpyyyy/ESPSomfy-RTS/blob/v4.1.0/src/WebAuth.cpp))

**cjkas has the strongest inspected defense-in-depth design:** centralized token checks for non-public HTTP routes and WebSockets when secured, upload checks, a private random HMAC key, constant-time comparisons, login throttling, narrowed static-file serving and restricted production CORS. Its limitations remain explicit: HTTP/WS traffic is unencrypted, tokens do not expire, and None mode intentionally permits access. Its release provenance attestations/checksums do not prove device-enforced firmware signatures or Secure Boot. ([Stable middleware](https://github.com/cjkas/ESPSomfy-RTS/blob/v4.0.2/src/entryPoints/Web.cpp), [threat model](https://github.com/cjkas/ESPSomfy-RTS/blob/main/docs/SECURITY_PLAN.md), [release trust](https://github.com/cjkas/ESPSomfy-RTS/blob/main/SECURITY.md))

Update transport is another distinction. Original upstream and inspected xkain updater code bypass GitHub certificate validation with `setInsecure()`. Current linuxrrze and Pulpyyyy source adds CA-based verification, although linuxrrze retains an insecure option/fallback. cjkas removes this download surface entirely. A checksum supplied beside a download detects corruption; it does not independently authenticate malicious replacement of both files. This review did not include penetration testing, fuzzing, a dependency-advisory audit or complete endpoint coverage. No “vulnerability-free” claim is justified. ([xkain updater](https://github.com/xkain/ESPSomfy-RTS/blob/f55fb4cc5aa36ccbc9434ff2bd28a17efd04c628/src/GitOTA.cpp), [linuxrrze policy](https://github.com/linuxrrze/ESPSomfy-RTS/blob/e3c1289c3bd06722dd32654df84e8c9039d43040/GitOTA.cpp), [Pulpyyyy TLS](https://github.com/Pulpyyyy/ESPSomfy-RTS/blob/731ffb35944a53ddf071104d4358d72372032efd/src/GitOTA.cpp))

**Somfy and Bruce can be alternative boots, not concurrent independent firmware.** Bruce's official compatibility table lists the exact Plus. bmorcelli/Launcher supports the T-Embed family, multiple installed applications and dynamic partitions. ESP-IDF selects one application to boot; the S3's two cores do not create separate firmware environments. While Bruce runs, the lilygo's Somfy HA/API service is offline, although the independent old remote still works. ([Bruce compatibility](https://bruce.computer/), [Launcher architecture](https://github.com/bmorcelli/Launcher/wiki/Explaining-the-project), [ESP-IDF bootloader](https://docs.espressif.com/projects/esp-idf/en/latest/esp32s3/api-guides/bootloader.html))

Our exact Somfy/Bruce/Launcher arrangement is **unverified**. Their partition layouts differ, and both applications use a default LittleFS label; a launcher can reuse matching data partitions. NVS, Wi-Fi credentials, identities and rolling counters need explicit preservation/isolation. Ordinary Somfy OTA could also overwrite the other application slot. The existing OTA slots are not automatically a safe dual-boot setup. A full configured flash/NVS backup under issue #9 must precede experiments. A merged firmware would require shared-radio arbitration, scheduling and persistence engineering. Keeping Somfy dedicated and using another device for Bruce is the simpler reliable arrangement. ([Bruce partitions](https://github.com/BruceDevices/firmware/blob/1.16.1/custom_16Mb.csv), [Launcher partition/data handling](https://github.com/bmorcelli/Launcher/blob/main/src/partition_install_layout.cpp), [OTA model](https://docs.espressif.com/projects/esp-idf/en/stable/esp32s3/api-reference/system/ota.html))

**A Rust controller is technically feasible today.** ESP32-S3 uses Xtensa and currently needs Espressif's Rust toolchain. The pragmatic prototype uses Rust `std` with ESP-IDF service/driver bindings, retaining C/FreeRTOS networking, HTTP/WebSockets, NVS and OTA. These crates now live in the esp-rs/esp-idf monorepo; the old svc repository was archived because it moved. A `no_std`/esp-hal design owns more of the system; S3 RMT can emit/capture pulse sequences, but that driver currently has an unstable API. ([Toolchain](https://github.com/esp-rs/book/blob/main/src/getting-started/toolchain.md), [current monorepo](https://github.com/esp-rs/esp-idf), [RMT](https://docs.espressif.com/projects/rust/esp-hal/main/esp32s3/esp_hal/rmt/index.html))

Existing [somfy-rs](https://github.com/reitermarkus/somfy-rs) framing/storage abstractions could reduce protocol work, but its Raspberry Pi/Linux dependencies prevent treating it as ESP32 firmware unchanged. The demanding parts remain exact OOK timing, brownout-safe counters, safe restore/rollback, format-24 migration and HA event/API compatibility. Safe Rust reduces memory defects in newly written code; it does not automatically repair authorization, TLS, C dependencies or Somfy's radio protocol. ([Manifest](https://github.com/reitermarkus/somfy-rs/blob/main/Cargo.toml), [NVS semantics](https://docs.espressif.com/projects/esp-idf/en/stable/esp32s3/api-reference/storage/nvs_flash.html))

I would evaluate a maintained C++ baseline for the working controller and treat Rust as an isolated engineering project: host-test protocol/state modules, then prototype on a spare board before migration. This separates household availability from experimentation and makes it possible to verify counter durability and security boundaries without risking the paired bedroom controller. No physical verification should resume until the user explicitly authorizes it.
