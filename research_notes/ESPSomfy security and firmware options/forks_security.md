# Fork differentiators and targeted code security

Snapshot: 2026-11-03, America/Los_Angeles. Public source inspection only. No requests were sent to the user's controller, no live vulnerability testing, installation, security setting change, or motor commands. This is a bounded desk review, not a complete security audit, formal vulnerability assessment or dependency-advisory audit.

## What meaningfully differentiates the branches?

### Takeaway
cjkas is a substantial architecture, reliability and security redesign. xkain is closer to the original operating model with a redesigned localized UI. linuxrrze emphasizes the classic updater/recovery path. Pulpyyyy is a more heavily evolved classic-controller derivative with safer update/RF scheduling work. Activity is not itself a security guarantee.

### Cited Findings
- **Original rstrouse:** Arduino-era synchronous WebServer on ports80/8081, original event sockets and manual/GitHub updates. Its original behavior remains the user's currently working custom hardware port. [Web implementation](https://github.com/rstrouse/ESPSomfy-RTS/blob/eb75868adb92b3e6f5d3ead069f915d84a72efde/Web.cpp).
- **cjkas:** asynchronous web/sockets, command handoff to the loop task, newer Arduino3/ESP-IDF5.5 generation, additional C5/C6/P4 targets, one HTTP/WebSocket port80, RAM-built backups, maintained matching HA component, and release checksums/build attestations. It removes device-side GitHub downloads; uploads or USB remain. Current source pins Arduino3.3.12/IDF5.5 and exact library versions. Claims such as “no random restarts” are maintainer claims, not tested on this Plus. [README](https://github.com/cjkas/ESPSomfy-RTS/blob/f17eb4c7bbf68b4bd64456be415022746e698f1f/README.md), [build](https://github.com/cjkas/ESPSomfy-RTS/blob/f17eb4c7bbf68b4bd64456be415022746e698f1f/platformio.ini), [ADR0007](https://github.com/cjkas/ESPSomfy-RTS/blob/main/docs/adr/0007-no-github-update.md).
- **xkain:** strongly emphasizes mobile/responsive UI, dark/localized presentation, GPIO selectors/presets and original HA compatibility. Its migration notice warns older backup radio pin assignments are not automatically restored; manually verify GPIOs. This matters for our fixed integrated Plus wiring. [README](https://github.com/xkain/ESPSomfy-RTS/blob/f55fb4cc5aa36ccbc9434ff2bd28a17efd04c628/src/README.md). The separate xkain Enhanced repository is a HA integration, not the firmware.
- **linuxrrze:** retains the original UI/architecture more closely and adds own-repository GitHub update/recovery, a web installer, preserving-state repair paths, update checking and optional unattended installs in a3–4am window. This is importantly different from cjkas removing remote downloads. Do not enable unattended updates on our custom profile. [README](https://github.com/linuxrrze/ESPSomfy-RTS/blob/e3c1289c3bd06722dd32654df84e8c9039d43040/README.md), [updater](https://github.com/linuxrrze/ESPSomfy-RTS/blob/e3c1289c3bd06722dd32654df84e8c9039d43040/GitOTA.cpp).
- **Pulpyyyy:** latest stable release notes describe RF serialization/frame spacing, update preflight/failure recovery and safer filesystem updates; its updater selects S3 4MB/8MB variants, not our exact Plus profile. [v4.1.0 release](https://github.com/Pulpyyyy/ESPSomfy-RTS/releases/tag/v4.1.0), [updater](https://github.com/Pulpyyyy/ESPSomfy-RTS/blob/731ffb35944a53ddf071104d4358d72372032efd/src/GitOTA.cpp).

### Inferences
- cjkas is the strongest candidate to evaluate as a maintained platform, especially for reliability/security architecture; xkain is a lower-contract-change alternative if retaining the existing HA/API shape matters. Neither is yet proven compatible with our Plus initialization/partition/configuration.
- A migration is not a one-file upgrade. cjkas4.x changes ports/socket protocol and needs its newer HA component and USB provisioning/restore from original firmware. [Migration instructions](https://github.com/cjkas/ESPSomfy-RTS#readme).

### Gaps
- No comparative load/latency/hardware tests, configuration migration or fork binaries were run. Exact Plus-profile release support remains unconfirmed by earlier research.

## What does source inspection establish about security?

### Takeaway
The original code has serious LAN-boundary weaknesses. Some forks contain concrete fixes; cjkas has the clearest inspected defense-in-depth design. None should be described as audited or safe for direct Internet exposure, and all inspected configurations default to Security=None.

### Cited Findings
- **Original authentication gap:** `Web::isAuthenticated` exists, but the inspected upstream Web.cpp contains no callers enforcing it on registered routes. The firmware-upload and configuration handlers are registered directly. xkain explicitly documents the inherited omission in its new guard implementation. Therefore setting a UI PIN is not evidence that every privileged endpoint is protected. This is source evidence, not a demonstrated exploit against the user's device. [Original helper/routes](https://github.com/rstrouse/ESPSomfy-RTS/blob/eb75868adb92b3e6f5d3ead069f915d84a72efde/Web.cpp), [xkain explanation/guard](https://github.com/xkain/ESPSomfy-RTS/blob/f55fb4cc5aa36ccbc9434ff2bd28a17efd04c628/src/Web.cpp).
- **Original credential disclosure/storage:** `SecuritySettings::toJSON` returns password/PIN, while save/load store them as Preferences strings in SEC NVS. The inspected code does not establish flash/NVS encryption. These secrets and tokens traverse HTTP where accessed through the device web API. [Original settings](https://github.com/rstrouse/ESPSomfy-RTS/blob/eb75868adb92b3e6f5d3ead069f915d84a72efde/ConfigSettings.cpp). The current user's custom board patch did not replace this auth design.
- **Original/xkain update transport:** inspected GitOTA.cpp calls `WiFiClientSecure::setInsecure()` for GitHub HTTPS operations, which bypasses server certificate validation. HTTPS syntax alone does not establish authenticated download transport. No artifact-signature enforcement was established in those inspected paths. [Original OTA](https://github.com/rstrouse/ESPSomfy-RTS/blob/eb75868adb92b3e6f5d3ead069f915d84a72efde/GitOTA.cpp), [xkain OTA](https://github.com/xkain/ESPSomfy-RTS/blob/f55fb4cc5aa36ccbc9434ff2bd28a17efd04c628/src/GitOTA.cpp).
- **xkain concrete fixes:** latest stable v2.6.1 already wraps both HTTP servers' routes and upload handlers in guards, classifying absent routes as Config; it distinguishes control reads from configuration writes, masks sensitive remote/counter information, and makes password/PIN JSON write-only (`hasPassword`/`hasPin`). It also implements login lockouts. Authentication still passes when Security=None and may permit control in ConfigOnly mode. Its current token HMAC remains keyed by public serverId rather than cjkas's private random key. [Stable guards](https://github.com/xkain/ESPSomfy-RTS/blob/v2.6.1/src/Web.cpp), [stable secret serialization](https://github.com/xkain/ESPSomfy-RTS/blob/v2.6.1/src/ConfigSettings.cpp).
- **linuxrrze concrete fixes and limit:** v2.4.19 contains an AuthHandler in front of UI routes/uploads and default-protects UI configuration routes. It explicitly leaves most port8081 API routes public for legacy HA compatibility, protecting only selected API configuration endpoints, so its protected UI does not imply authenticated motor control on every port. GitHub release/download TLS now uses a CA bundle by default, with an explicit insecure mode/fallback; a connectivity-only probe still uses setInsecure. [Stable auth](https://github.com/linuxrrze/ESPSomfy-RTS/blob/v2.4.19/Web.cpp), [trust policy](https://github.com/linuxrrze/ESPSomfy-RTS/blob/e3c1289c3bd06722dd32654df84e8c9039d43040/GitOTA.cpp).
- **Pulpyyyy concrete fixes:** stable v4.1.0 includes an ensureAuth gate, same-origin/Host validation intended to address cross-site and DNS-rebinding requests, private/random token-secret handling and constant-time comparison. Current GitHub operations use bundled root CAs instead of setInsecure. These are specific source improvements, not a full endpoint-coverage proof. [Stable WebAuth](https://github.com/Pulpyyyy/ESPSomfy-RTS/blob/v4.1.0/src/WebAuth.cpp), [TLS code](https://github.com/Pulpyyyy/ESPSomfy-RTS/blob/731ffb35944a53ddf071104d4358d72372032efd/src/GitOTA.cpp).
- **cjkas concrete fixes:** v4.0.2 central middleware requires the token for every non-public HTTP route when Secured, with separate first-chunk upload checks and a token/Origin check for the socket. Private32-byte random HMAC key stored in NVS, constant-time comparison, per-IP exponential login throttling, write-only secret serialization and narrowed static-file serving are documented and visible in current code. CORS wildcard headers are compiled only under development WEB_CORS; release configuration leaves it off. [Stable middleware](https://github.com/cjkas/ESPSomfy-RTS/blob/v4.0.2/src/entryPoints/Web.cpp), [token comparator](https://github.com/cjkas/ESPSomfy-RTS/blob/f17eb4c7bbf68b4bd64456be415022746e698f1f/src/ApiToken.h), [security design](https://github.com/cjkas/ESPSomfy-RTS/blob/main/docs/SECURITY_PLAN.md), [two modes/ports](https://github.com/cjkas/ESPSomfy-RTS/blob/main/docs/adr/0006-two-security-modes-eleven-http-routes.md).
- **cjkas remaining limits:** plain HTTP/WS remains; traffic sniffing and direct Internet exposure are outside its stated threat model. Tokens do not expire. None mode intentionally leaves controls open, and enabling Secured is a separate configuration decision. These limits are explicitly documented, not inferred as solved by newer dependencies. [Threat model and exclusions](https://github.com/cjkas/ESPSomfy-RTS/blob/main/docs/SECURITY_PLAN.md).
- **Release trust:** cjkas SECURITY.md documents GitHub signed build attestations and SHA256SUMS starting after4.0.1, pinned actions/dependencies and CodeQL/zizmor/Scorecard workflows. An attestation can verify provenance on the downloading computer; this is not evidence of device-enforced signed firmware, Secure Boot or encrypted NVS. [Security/release verification policy](https://github.com/cjkas/ESPSomfy-RTS/blob/main/SECURITY.md).

### Inferences
- For this installation, the immediate defensible posture is a LAN-only control plane with only intended management/HA clients able to reach it, plus no generic upstream firmware updates. Network restrictions can contain a vulnerable application but do not repair it. No firewall/network changes were made here.
- cjkas appears materially stronger by inspected design and testing practices; this is not an independent audit or a promise of safety. Keep security review a separate criterion from features/commit volume.
- The shared original radio protocol/rolling-code behavior is not made cryptographically stronger merely by changing the web UI or choosing Rust. The Web/API/auth/transport and RF protocol are separate trust boundaries.

### Gaps
- No live authenticated/unauthenticated endpoint probes, penetration test, native dependency CVE audit, fuzzing, formal analysis, signing-enforcement or Secure Boot verification. No numeric security grades or zero-vulnerability claims are justified.
- Current-main source and documentation can be ahead of releases. Stable tags were explicitly checked for the guards listed above (xkain2.6.1, linuxrrze2.4.19, cjkas4.0.2, Pulpyyyy4.1.0); deeper claims such as build tooling/TLS should be treated as current-source observations unless their linked tag proves otherwise.
